# سير العمل

## Git
- **Trunk-based:** الفرع `main` دائمًا قابل للنشر.
- فروع قصيرة العمر (يوم إلى يومين): `feat/<وصف>` و`fix/<وصف>` (و`docs/…`, `chore/…`).
- **PR** إلى `main` بمراجعة واحدة على الأقل، وCI أخضر قبل الدمج (squash).
- **Conventional commits:** `feat(editor): add auto-rewind`، `fix(text-engine): normalize alef variants`، `docs:`، `test:`، `chore:`.

## تعريف الإنجاز (Definition of Done)
1. الكود مُراجَع (PR موافَق عليه).
2. الاختبارات الآلية تمر في CI.
3. واجهة عربية RTL مفحوصة يدويًا (الاتجاه، الخطوط، الأرقام، الاختصارات).
4. اعتماد QA على معايير القبول.
5. منشور على بيئة staging.

## توجيه المهام بين Opus وSonnet
| النموذج | نوع المهام |
|---|---|
| **Opus** | خوارزميات المطابقة (بحث القرآن/الحديث، كشف الآيات)، ASR وتقييمه، تخطيط التصدير (Word/PDF RTL)، الأمان والصلاحيات، التحقق بـ SHA-256، القرارات المعمارية |
| **Sonnet** | CRUD، شاشات الواجهة، التوثيق، الإعدادات وCI، الاختبارات الروتينية |

القاعدة: إن كان الخطأ فيها يُفسد نصًا دينيًا أو يكسر الأمان أو يحتاج استدلالًا خوارزميًا، فهي Opus؛ وإلا Sonnet. كل مهمة في `docs/sprints.md` تحمل وسمًا مقترحًا ويمكن للقائد تغييره. مخرجات Sonnet الحساسة تُراجع بواسطة Opus.
